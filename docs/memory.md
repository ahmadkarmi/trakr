## 2026-07-22 — Offline photo-capture outbox (Phase 4 follow-up, the deferred feature)
- **Built the offline outbox** deferred earlier. A section photo is now persisted to **IndexedDB** on capture (before any network call) and replayed when online, so a capture during a field audit with no signal is never lost. New `utils/photoOutbox.ts` (raw IndexedDB — no new deps), `hooks/usePhotoOutbox.ts` (`useSyncExternalStore`), `<SignedImage>` renders pending tiles from a `blob:` URL (passthrough) with pending/uploading/failed badges + Retry/Discard. `AuditWizard.onFilesSelected` enqueues instead of uploading; flush triggers on load / `online` / `visibilitychange`; `purgeConfirmed` drops a record once the refetched audit shows its server row (flicker-free swap).
- **Exactly-once replay** = deterministic object path `audits/<auditId>/outbox-<clientId>` + a **UNIQUE index on `audit_photos.url`** (migration `20260722153815`) as the DB arbiter; `addSectionPhoto` gained an optional `clientId` and treats a `23505` as success (reads back the winner). A pre-insert existence check is only a fast path — the unique index is the real guarantee (a select-then-insert TOCTOU can't be atomic across tabs).
- **Design + review were multi-agent** (ultracode): a 9-agent scout+design workflow produced the spec; a separate adversarial-review workflow (5 finder dimensions → per-finding verifiers) found **9 confirmed defects**, all fixed before merge — the review paid for itself. Key bugs caught: (1) `enqueue` resolved on IDB *request* success not *transaction commit*, so a commit-time quota abort silently "succeeded" and lost the blob → resolve writes on `tx.oncomplete`; (2) a record stranded at `uploading` by a crash/reload was never re-selected (flush filters `pending`) → reclaim stale `uploading`→`pending` at flush start (safe via exactly-once); (3) no unique constraint → concurrent multi-tab flush duplicated rows → the unique index above; (4) `openDb()` cached a *rejected* promise, disabling the outbox forever after one transient failure → null the memo on error/blocked; (5) the insert-failure compensating `storage.remove` deleted the *shared* deterministic object a concurrent winner owned → skip compensation on the `clientId` path; (6) `objectURL`s leaked → `evictSection` revokes on unmount/section-change (skipping in-flight `uploading`); (7) discarding a record mid-upload orphaned the server row → disable Remove while `uploading`.
- **Tests**: pure-logic unit tests (backoff/permanence/merge) run in the gated `checks` job; the IDB round-trip is a Playwright e2e (`audit.offline-photo.spec.ts`) using real browser IndexedDB — proves offline capture → durable IDB → **crash-simulated `uploading` reclaim** → reconnect flush → **exactly one** row → reload re-flush still one row. (An offline *page reload* can't be tested on the Vite dev server — `setOffline` blocks the localhost document too; a direct IDB read proves durability more strongly. jsdom has no IndexedDB, hence e2e not unit for the round-trip — kept the no-new-deps veto by not adding `fake-indexeddb`.)

## 2026-07-22 — Storage isolation, part 2: privatize profile-media (Phase 1a-2)
- Privatized the `profile-media` bucket (avatars + signatures) and org-scoped it, reusing the 1a-1 signing infra (`<SignedImage>` + `useSignedUrl`) across **17 display sites** (7 avatar components, 3 signature sites, the approval-signature panel). Both media buckets are now private and org-partitioned; no bucket-only storage policy remains.
- **Path scheme changed** to `<prefix>/<userId>/...` (clean folder segment) — safe because there was zero stored profile-media data. Writes are **own-only** (`folder[2] = current_user_id()`); reads are **same-org** (via `storage_user_in_my_org()` SECURITY DEFINER, mirroring `storage_audit_in_my_org`). All `setUserAvatar`/`setUserSignature` callers pass `user.id` (self), so own-only writes break nothing. Approval signatures render through the same resolver — drawn ones are inline `data:` URLs (pass-through), image-mode ones are profile-media paths (signed).
- **Gotcha (anon EXECUTE)**: Supabase default privileges grant EXECUTE to `anon` *explicitly* on new public functions, so `REVOKE … FROM PUBLIC` alone does NOT clear the anon grant — you must also `REVOKE … FROM anon`. The 1a-1 helper looked clean only because it happened to get both a `FROM anon` and a `FROM PUBLIC` revoke. **Rule**: to lock a new public function to authenticated-only, `REVOKE EXECUTE … FROM PUBLIC, anon; GRANT … TO authenticated;`.

## 2026-07-22 — Storage isolation, part 1: privatize audit-photos + signed-URL layer (Phase 1a-1)
- **CRITICAL closed**: the `audit-photos` bucket was `public=true`, so audit evidence was **internet-readable by URL**, and the only `storage.objects` policies were scoped by `bucket_id` alone — any authenticated user of org A could read/overwrite org B's photos. Privatized the bucket and org-scoped object access on the `audits/<auditId>/...` path segment.
- **Key discovery that reshaped the risk**: the live pilot has **zero real stored assets** (`audit_photos` 0 rows, all `avatar_url`/`signature_url` null) — the 195 storage objects are all e2e artifacts. So privatizing broke no existing pilot data; ideal timing to fix before real evidence lands. Also found the profile-media path scheme embeds userId in the filename with UUID hyphens (ambiguous) — deferred to 1a-2 where the scheme can change freely (no data).
- **Org-scoping needs a SECURITY DEFINER helper**: the first predicate used `EXISTS(SELECT 1 FROM public.audits …)` inside the policy, but that subquery runs under the **caller's** RLS — an auditor can't SELECT an *unassigned* org audit, so org membership couldn't be checked and the in-org object was (wrongly) hidden. Fixed with `storage_audit_in_my_org(uuid)` SECURITY DEFINER (bypasses audits RLS, pins search_path, `REVOKE EXECUTE FROM PUBLIC` so anon can't call it). **Rule**: storage/RLS predicates that must authorize on a row the caller can't necessarily SELECT need a definer helper, not a bare EXISTS. The path `::uuid` cast is regex-guarded (`~ '^[0-9a-fA-F-]{36}$'`) so a malformed path fails closed (AND short-circuits) instead of erroring.
- **Signed-URL layer (new pattern, user-approved per CLAUDE.md §4)**: private buckets can't serve `getPublicUrl`, so the app stores the object **path** and signs on read. Signing happens at **display time** (`utils/signedUrls.ts` + `useSignedUrl` hook + `<SignedImage>`), NOT at fetch time — because this app persists the whole React Query cache to localStorage with `staleTime: Infinity`, a signed URL cached in a query would be written to disk and 404 after it expires. The resolver passes through `data:`/`blob:`/`http` values (drawn signatures, legacy URLs) untouched. PDF signs inline before embedding.
- **Staged deliberately**: audit-photos (the actual evidence, ~6 sites) shipped first; **profile-media** avatars/signatures (wider surface: 7 avatar components + 3 signature sites, lower sensitivity) stays public until the 1a-2 follow-up, which reuses this same infra.
- **Proof**: role-switched rollback transactions (in-org SELECT/INSERT allowed, foreign + malformed-path DENIED) + `get_advisors` (zero ERROR lints; the `authenticated_security_definer_function_executable` warning on the helper is the same by-design pattern as `current_user_org_id` et al.). Realigned `storage.uploads.spec` — **5/5 green** against the now-private live DB, including a signed-URL **fetch → 200** round-trip (the real display/PDF path) and a foreign-audit-path upload denial.

## 2026-07-22 — Verification & hardening: audit-integrity + cross-org RPC guards (Phases 0, 1b, 1c)
- **Context**: read-only investigation (20-agent workflow + adversarial verification) of the live pilot DB found the real cross-tenant/integrity risks are NOT at the table-RLS layer (all 19 tables are correctly org-scoped) but in three places table policies don't reach. Fixed riskiest-first, each proven red→green on the live DB via non-persisting rollback transactions before applying, then gated behind CI.
- **Phase 0 (#124)** — `packages/shared` had **no test runner in CI** (`calculateWeightedAuditScore` was untested; a characterization test dropped in would be collected by nothing → false green). Wired `vitest` + `test:run` + a required `@trakr/shared` CI step so every later scoring/state proof actually gates PRs. Prereq for everything below.
- **Phase 1b (#125) — CRITICAL: auditor could self-approve.** `audits_update_policy`'s `WITH CHECK` imposes no status constraint, so a raw `update({status:'APPROVED'})` from the assigned auditor bypassed every guard in `set_audit_approval` (self-approval block, `WHERE status='SUBMITTED'`, signature capture) — a compliance-fraud vector. `WITH CHECK` can't see `OLD.status`, so enforced the state machine with a **BEFORE UPDATE trigger** (`enforce_audit_status_transition`, migration `20260722094148`). SECURITY **INVOKER** deliberately: `current_user` is then `authenticated` for raw PostgREST calls (constrained: auditor → DRAFT/IN_PROGRESS/COMPLETED only) but `postgres` inside the SECURITY DEFINER RPCs and service_role (pass through). Proven: without the trigger the self-approve succeeds; with it, 42501.
- **Phase 1c (#126) — HIGH: cross-org RPC mutation.** Eight SECURITY DEFINER RPCs (`reassign_*`, `set_audit_assigned_to`, `set_auditor_assignment`, `remove_*_from_auditor_assignments`, `submit_audit`) were RLS-bypassing, granted to `authenticated`, and had **no org check** — org A could reassign/submit org B's audits and rewrite org B users' assignments. Added org+role guards mirroring `create_audit_with_cycle_guard`; `submit_audit` now requires the assigned auditor or an admin and derives `submitted_by` from `auth.uid()`; pinned `search_path` on the three the advisor flagged. **Gotcha (two migration stamps `20260722100541`+`101613`)**: the first cut guarded on `is_admin_or_super()` only, which is false for the trusted **service_role** backend (`auth.uid()` is null there) and broke the seeder/edge/e2e path (`ensureAuditorAssignedToBranch` calls `set_auditor_assignment` via service_role) — the correction allows `auth.role()='service_role'` alongside an in-org admin. **Rule**: SECURITY DEFINER guards that must also serve the backend key check `is_admin_or_super() OR auth.role()='service_role'`, never `is_admin_or_super()` alone.

## 2026-07-22 — Weighted scoring: flagged semantic decisions (Phase 2)
- **Decision**: `calculateWeightedAuditScore` is **mathematically sound** — divide-by-zero is guarded (returns 0), N/A is excluded from the denominator, overrides are clamped to `[0, maxPoints]`. Locked all of that as a characterization regression net (`packages/shared/src/utils/scoring.test.ts`, 17 tests). Did **not** change any behavior; per the hardening plan, suspected-wrong semantics are **flagged for a product decision**, not silently "fixed".
- **Open questions captured as `FLAG:` tests (each asserts the CURRENT number, NOT an endorsement)**:
  1. **Unanswered excluded → partial audits inflate**: compliance is over *answered* questions only, so 1-of-100 answered "yes" reports 100%. Completion is a separate, unshown metric. Decide whether the score should gate behind a completion threshold.
  2. **No weighted questions → real-looking 0%** indistinguishable from fully non-compliant. Decide on a null/NaN sentinel or `hasWeightedQuestions` flag so the UI can render "N/A".
  3. **`maxPoints = max(yesWeight, noWeight)`** → an all-"yes" audit scores <100% when `noWeight > yesWeight`. Is `noWeight > yesWeight` ever a valid authoring state?
  4. **Override ignored unless response is exactly "na"** — setting a score on an *unanswered* question has no effect.
  5. **NaN override poisons the whole score** (no `Number.isFinite` guard) — the one concrete code fix suggested. Low reachability (UI writes numbers) but cheap to harden.
  6. **Whitespace/non-canonical response (" yes ") scores nothing** — matching is `toLowerCase() === 'yes'` with no trim.
  7. **Three divergent "weighted" definitions**: `calculateWeightedAuditScore` (pooled ratio) vs `calculateSectionWeightedCompliance` (section-fraction × *unweighted* yes-ratio) can differ by >40 points on the same audit (test shows 99% vs 50%); `calculateSectionWeightedWeightedCompliance` is just an alias of the first. Only one can be canonical to the bank — consolidate the 11 call sites once product decides. **Recommended canonical: `calculateWeightedAuditScore`** (it's the only one that actually honors per-question weights).

## 2026-07-10 — Audit-trail FK fix + cross-user notifications were broken (RETURNING vs SELECT policy)
- **`log_data_access` wrote `auth.uid()` directly as `data_access_audit.user_id`** — FK to `users(id)` failed for seeded users (`users.id ≠ auth.uid()`), breaking `set_org_config` (Settings → Super Admin toggles). Fixed with the tolerant caller lookup (migration `20260710071516`); verified: toggle flips in the UI, audit trail records the app user id.
- **Cross-user notification delivery was genuinely broken** (auditor submits → manager/admin never notified; every same-org send from the client failed RLS 42501). Root cause is subtle: the INSERT policy allows same-org sends, but `createNotification` called `.insert(...).select()` — and **`INSERT … RETURNING` requires the new row to also satisfy the SELECT policy** (`user_id = current_user_id()`), which the sender of a cross-user notification can never satisfy. Self-notifications passed, cross-user always failed; notifications visible in the UI came from the service-key seeder. Fix: drop the unused `.select()`. Also removed the legacy auth-id-first insert probe that guaranteed one FK/RLS ERROR log per notification by design.
- **Rule of thumb recorded**: never chain `.select()` onto an insert whose row the inserter may not be able to read back — on self-scoped-SELECT tables (notifications is the only one today), RETURNING turns an authorized write into an RLS failure. A mid-investigation policy recreation (migration `recreate_notifications_insert_policy...`) was a semantic no-op — trees were byte-identical; the file is kept for stamp parity.

## 2026-07-09 — Storage upload RLS regression (found by the revived integration tests)
- The 2026-07-03 storage hardening dropped all SELECT policies on `storage.objects` ("reads go via public URLs") — but the storage upload path needs SELECT on the row it inserts, so **every authenticated upload failed in production since then**. Restored as `app_media_select`, SELECT **to authenticated only**, scoped to the two media buckets (anon enumeration stays blocked). Migration `20260709194139`.
- **Lesson**: e2e has zero upload coverage; the vitest storage suites that would have caught this were invisibly broken (skipped in CI, transport-dead locally). When a test suite is "always failing/skipped", it's masking real bugs, not just being noisy.

## 2026-07-09 — QA sandbox findings
- **Persisted query cache must stay JSON-safe**: `main.tsx` persists the entire React Query cache to `localStorage` via `JSON.stringify` (`PersistQueryClientProvider`). Non-serializable query data (`Set`, `Map`, `Date`, class instances) silently corrupts on the round-trip (`Set` → `{}`), and with `staleTime: Infinity` never self-heals. Store plain arrays/objects in queries; derive `Set`/`Map` with `useMemo` outside the cache. Found via a `derivedReadIds.has is not a function` error-boundary crash in `useNotifications.ts`.
- **Enum casts in SQL functions are explicit**: Postgres implicitly casts a bare `'LITERAL'` to an enum column but *not* a `COALESCE(...)` expression result — `handle_new_user()` had failed on every fresh `auth.users` insert (the app's first-login auto-provision path) until `::user_role` was added (migration `20260709124151`).
- **QA sandbox org added** ("Trakr QA Sandbox", `scripts/seed-qa-org.mjs` + `scripts/qa-smoke.mjs`): persistent per-role accounts and all-six-status audit data for browser QA. Both bugs above were invisible to `tsc`, unit tests, and the e2e suite — surfaced only by exercising real screens with varied data.

## 2026-07-03 — Production cleanup baseline
- **Trunk-based flow adopted**: protected `main`, short-lived branches, squash merges, CI (`ci.yml`) + E2E (`e2e.yml`) gates. Scratch files never land at root.
- **E2E serialized** via `e2e-shared-db` concurrency group — the suite seeds/mutates one shared database; concurrent runs corrupt each other (proven 2026-07-03). Follow-up: dedicated test project.
- **Migration discipline**: repo `supabase/migrations/` mirrors live `schema_migrations` stamps exactly; every schema change ships as migration + regenerated types in one commit.
- **`apps/mobile` removed** (parked in git history) — web PWA covers mobile until a native app is a priority.
- **Lint debt**: 531 pre-existing `no-explicit-any` errors; CI lint step is advisory until burned down.
- **Seeder invariant**: `seed-with-credentials.js` must link `users.auth_user_id` after recreating rows — unlinked rows are invisible to their own session under RLS.
